# Test Plan for Barbican Project (Revised)

This document outlines the plan for creating comprehensive unit tests for the `barbican` project, including MongoDB mocking and unit tests for `create_inbox` and `get_inbox` handlers.

## Overview

The barbican project is an Axum-based HTTP service that provides inbox management endpoints backed by MongoDB. The current implementation has:
- `POST /api/v1/inbox` - Creates a new inbox
- `GET /api/v1/inbox/{id}` - Retrieves an inbox by ID

## Architecture

### Error Handling Strategy

- Custom `AppError` enum using `thiserror` for structured error types
- Error variants map to appropriate HTTP status codes
- User-facing error messages are sanitized; full details logged at debug level
- `AppError` implements `IntoResponse` for automatic HTTP response conversion

### Abstraction Layers

1. **Domain Layer**: `InboxStore` trait abstracts database operations
2. **Adapter Layer**: `MongoInboxStore` implements the trait for real MongoDB
3. **Test Layer**: `MockInboxStore` auto-generated by `mockall` for unit tests

## Phase 1: Error Type Infrastructure

### 1.1 Create AppError Enum

**File**: `barbican/src/error.rs`

Define structured error types using `thiserror`:

```rust
use thiserror::Error;
use axum::{http::StatusCode, response::{IntoResponse, Response}, Json};
use serde::Serialize;

#[derive(Error, Debug)]
pub enum AppError {
    #[error("Validation error: {0}")]
    ValidationError(String),
    
    #[error("Not found: {0}")]
    NotFoundError(String),
    
    #[error("Database error: {0}")]
    DatabaseError(String),
    
    #[error("Internal error: {0}")]
    InternalError(String),
}

impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        #[derive(Serialize)]
        struct ErrorResponse {
            message: String,
        }
        
        let (status, message) = match &self {
            AppError::ValidationError(msg) => (StatusCode::BAD_REQUEST, msg),
            AppError::NotFoundError(msg) => (StatusCode::NOT_FOUND, msg),
            AppError::DatabaseError(msg) | AppError::InternalError(msg) => {
                (StatusCode::INTERNAL_SERVER_ERROR, msg)
            }
        };
        
        (status, Json(ErrorResponse { message: message.clone() })).into_response()
    }
}
```

## Phase 2: MongoDB Mocking Infrastructure

### 2.1 Define Database Trait

**File**: `barbican/src/db_trait.rs`

Create a trait that abstracts MongoDB operations with simplified return types:

```rust
use async_trait::async_trait;
use mockall::automock;
use mongodb::{bson::{doc, oid::ObjectId, Document}};
use crate::{InboxDB, error::AppError};

#[automock]
#[async_trait]
pub trait InboxStore: Send + Sync {
    async fn insert_one(&self, inbox: InboxDB) -> Result<ObjectId, AppError>;
    async fn find_one(&self, filter: Document) -> Result<Option<InboxDB>, AppError>;
}
```

The `#[automock]` attribute generates `MockInboxStore` automatically.

### 2.2 Implement Production Adapter

**File**: `barbican/src/db_adapter.rs`

Implement the trait for the actual MongoDB `Collection<InboxDB>`:

```rust
use async_trait::async_trait;
use mongodb::{Collection, bson::{doc, oid::ObjectId, Document}};
use crate::{InboxDB, db_trait::InboxStore, error::AppError};

pub struct MongoInboxStore {
    collection: Collection<InboxDB>,
}

impl MongoInboxStore {
    pub fn new(collection: Collection<InboxDB>) -> Self {
        Self { collection }
    }
}

#[async_trait]
impl InboxStore for MongoInboxStore {
    async fn insert_one(&self, inbox: InboxDB) -> Result<ObjectId, AppError> {
        self.collection
            .insert_one(inbox)
            .await
            .map(|result| result.inserted_id.as_object_id().unwrap())
            .map_err(|e| AppError::DatabaseError(e.to_string()))
    }

    async fn find_one(&self, filter: Document) -> Result<Option<InboxDB>, AppError> {
        self.collection
            .find_one(filter)
            .await
            .map_err(|e| AppError::DatabaseError(e.to_string()))
    }
}
```

### 3.2 Update Main Error Handling

**File**: `barbican/src/main.rs`

Extend the existing `AppError` to handle all application errors:

```rust
#[derive(Debug)]
enum AppError {
    JsonRejection(axum::extract::rejection::JsonRejection),
    Barbican(#[from] barbican::error::AppError),
}

impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        match self {
            AppError::JsonRejection(rejection) => {
                // Log at debug level with full details
                tracing::debug!(?rejection, "JSON rejection");
                // Return sanitized response
                (rejection.status(), Json(ErrorResponse { 
                    message: "Invalid request body".to_string() 
                })).into_response()
            }
            AppError::Barbican(err) => err.into_response(),
        }
    }
}
```

## Phase 4: Unit Tests for create_inbox

**File**: `barbican/src/handlers/create_inbox_tests.rs`

### 4.1 Success Cases

- **test_create_inbox_success**: 
  - Given a valid `CreateInbox` request
  - When the mock store successfully inserts
  - Then return `200 OK` with the ObjectId

- **test_create_inbox_with_minimal_data**:
  - Given a `CreateInbox` with minimum required fields
  - When inserted successfully
  - Then return success response

### 4.2 Error Cases

- **test_create_inbox_database_error**:
  - Given a mock store configured to return a database error
  - When create_inbox is called
  - Then return `500 Internal Server Error` with sanitized message

- **test_create_inbox_invalid_json**:
  - Given malformed JSON in request body
  - When the handler processes it
  - Then return `400 Bad Request`

## Phase 5: Unit Tests for get_inbox

**File**: `barbican/src/handlers/get_inbox_tests.rs`

### 5.1 Success Cases

2. **Phase 2** - Update trait and adapter to use `AppError`
3. **Phase 3** - Refactor handlers and main.rs error handling
4. **Phase 4** - Write create_inbox unit tests
5. **Phase 5** - Write get_inbox unit tests
6. **Phase 6** - Update test utilities as needed

## Success Criteria

- All unit tests pass with `cargo test`
- MongoDB mocking allows tests to run without a database connection
- Both success and error paths are covered for `create_inbox` and `get_inbox`
- Error messages to users are sanitized; full details logged at debug level
- No `#[non_exhaustive]` type construction issues in test code

## Notes

- The `#[automock]` attribute from mockall automatically generates `MockInboxStore`
- All tests use tokio test runtime
- Handlers are now properly decoupled from MongoDB implementation
- Integration tests are deferred to a later phase
- Use `tracing::debug!` for full error details, `tracing::error!` for sanitized user messages
