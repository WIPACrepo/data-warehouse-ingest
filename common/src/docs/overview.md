## Role in the Architecture

The data warehouse ingestion system has two services:

- [**Barbican**](../../barbican/src/docs/README.md) — the user-facing frontend that manages **inbox metadata** (CRUD) and orchestrates lifecycle operations.
- [**Citadel**](../../citadel/src/docs/README.md) — the backend that controls the **protected data areas** (file creation, transfer, deletion, job execution) and notifies downstream systems.

Barbican and Citadel must agree on a single vocabulary for inboxes: what an inbox is, what states it can be in, how progress is reported, and how errors are shaped. If these types drifted between the two services, coordination (state transitions, job callbacks, shared MongoDB collections) would break silently.

`common` exists to **prevent that drift**. It is a workspace library crate (declared in the root `Cargo.toml` as `common = { path = "common" }`) that both services depend on, and it contains only the shared types and utilities — no service business logic.

```
barbican/  ──┐
citadel/  ──┤──> depend on `common` (shared types + utilities)
common/   ──┘
```

## Ownership Boundary

Even though `common` is shared, it intentionally stays out of the business rules:

| Concern | Owned by | Where |
|---------|----------|-------|
| Inbox metadata CRUD & state machine | **Barbican** | `barbican/src/handlers`, `barbican/src/docs/state-machine.md` |
| Physical file operations & job execution | **Citadel** | `citadel/src/storage`, `citadel/src/jobs` |
| Shared data model (types, statuses, progress) | **`common`** | `common/src/models.rs` |
| Storage abstraction & MongoDB adapter | **`common`** | `common/src/traits.rs`, `common/src/adapters.rs` |
| Error contract & HTTP plumbing | **`common`** | `common/src/error.rs`, `common/src/middleware.rs`, etc. |

The rule of thumb: **if both services need it, it belongs in `common`; if only one service needs it, it belongs in that service.** This is why, for example, JWT/RBAC logic lives in `barbican/src/auth` and `citadel/src/auth` (service-specific), while `AppError` and the `InboxStore` trait live in `common` (shared).

## What `common` Provides

### 1. The Shared Data Model

The single source of truth for the inbox:

- `InboxDB` — the persisted MongoDB document
- `InboxStatus` — the 8-state lifecycle shared by both services
- `InboxProgress` — progress reporting for long-running operations
- `InboxError` — failure information recorded on an inbox
- `CreateInbox` — the request payload for creating an inbox

Documented in detail in [models.md](models.md).

### 2. The Storage Abstraction

- `InboxStore` trait — the async interface handlers depend on (insert/find/update/delete)
- `MongoInboxStore` — the MongoDB-backed implementation
- `MockInboxStore` — generated by `#[automock]` for tests

Documented in [infrastructure.md](infrastructure.md).

### 3. Error Handling

- `AppError` — the unified error enum with HTTP status mapping
- `AppJson` — a JSON extractor/response wrapper that formats rejections consistently
- `log_app_errors` — middleware hook for error logging

### 4. Infrastructure Utilities

- `db_setup`, `db_database`, `db_collection` — MongoDB client/database/collection helpers
- `logging_setup` — `tracing`/`tracing-subscriber` initialization with env-var filter control
- `shutdown_signal` — graceful shutdown (SIGINT/SIGTERM)
- `router_logging_layer` — `tower-http` trace + 10s request timeout
- `metrics_app`, `router_prometheus`, `start_metrics_server` — Prometheus metrics

### 5. Test Utilities

- `InboxBuilder`, `CreateInboxBuilder` — builder pattern for fixtures
- Fixture/helper functions (`create_test_inbox`, `create_test_store`, ...)
- `MockInboxStore` re-export (via `test_utils`)

Documented in [testing.md](testing.md).

## How the Services Consume `common`

### Barbican

Barbican re-exports and uses `common` heavily:

```rust
// barbican/src/lib.rs
pub use common::{CreateInbox, InboxDB, InboxStatus, InboxStore, MockInboxStore, MongoInboxStore};
```

In handlers it uses `common::AppError`, `common::AppJson`, `common::InboxDB`, `common::InboxProgress`, `common::InboxStatus`, and `common::InboxError`. In `main.rs` it uses `common::{db_setup, logging_setup, start_metrics_server}`. The router is wrapped with `common::router_logging_layer(...)` and `common::log_app_errors`, and the server shuts down via `common::shutdown_signal()`.

Barbican is the **writer** of inbox metadata: it creates `InboxDB` documents, performs state transitions, and persists progress — all through the `InboxStore` abstraction (in production, `MongoInboxStore`).

### Citadel

Citadel is the physical operator. It reads the shared model and works against the same MongoDB collection:

```rust
// citadel/src/db.rs
pub fn inboxes_collection(client: &Client, config: &CitadelConfig) -> Collection<common::models::InboxDB>
```

It uses `common::models::InboxDB` in its integrations (`barbican.rs`, `catalog.rs`, `lta.rs`) whenever it fetches or passes around inbox metadata. Citadel reads inbox metadata directly from the shared MongoDB `inboxes` collection (using `common::db::db_collection`), but transitions inbox state **only** through the Barbican API. Both services share the same `InboxStatus` vocabulary and `InboxDB` shape via `common`.

### The Shared MongoDB Collection

Because `` `common` `` defines a single `InboxDB` type and both services connect to the same `inboxes` collection through the same MongoDB helpers, a document written by Barbican can be read by Citadel (and vice versa) with no transformation layer.

## Dependencies & Policy

`common` depends on shared workspace dependencies (declared in the root `Cargo.toml` `[workspace.dependencies]`):

- `axum`, `axum-prometheus` — HTTP, router, metrics
- `mongodb`, `bson` — database
- `serde`, `serde_json` — serialization
- `tokio`, `tower-http`, `tracing`, `tracing-subscriber` — async, middleware, logging
- `async-trait`, `mockall` — async traits and mocking

Per the workspace `AGENTS.md`:

- Package versions are set in the workspace `Cargo.toml`, then referenced from workspace packages/libraries.
- Each crate keeps its own `src/tests/` directory with `test_utils/`.
- Integration tests requiring services (e.g., MongoDB) live in `tests/` and are gated behind the `integration-tests` feature flag.

> **Policy note:** `common` should not pull in service-specific logic (JWT libraries, filesystem operations, job executors). Keeping the dependency surface small keeps the shared library easy to reason about and fast to compile.

---

## Design Principles

1. **Single Source of Truth** — the inbox model and status set exist in exactly one place.
2. **Abstraction over Infrastructure** — code depends on `InboxStore`, not MongoDB, enabling fast unit tests.
3. **Consistent Error Contract** — `AppError` maps every failure to an HTTP status uniformly.
4. **Ownership by Need** — shared concerns live here; single-service concerns live in the service.
5. **Leverage the Workspace** — deps are shared; `common` is just another workspace member, not a published crate.
